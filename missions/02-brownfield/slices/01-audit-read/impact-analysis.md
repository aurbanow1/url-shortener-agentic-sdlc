## Change in one sentence

A read-only, cursor-paginated `GET /api/audit` returns the audit rows newest first by write
sequence. It serves only loopback clients that send no forwarding header. The shipped
configuration pins `server.forward-headers-strategy=none`, so no platform default can rewrite the
address the check reads. Requirements: FR-17, NFR-S6; FR-13, O1, O2 and M1 to M3 cross-cutting.

**Not touched:** `link/`, `click/`, `web/` and `db/migration/`. There is no migration (below),
and this slice takes no Flyway number.

## Impacted endpoints

| Method and path | Before | After |
|---|---|---|
| `GET /api/audit` | `404` problem (no handler) | `200` page from a loopback client without a forwarding header; `403` problem otherwise; `400` for a bad `limit` or `cursor`; `500` if the store fails; `429` when the client's create budget is spent |
| `HEAD /api/audit` | `404` | as `GET` without a body (P2j `200`, P2h `403`) |
| `POST`, `PUT`, `PATCH`, `DELETE /api/audit` | `404` | `405` problem, `Allow: GET` (P2i) |
| `OPTIONS /api/audit` | framework default | framework default, `Allow: GET,HEAD,OPTIONS` (P2k) |
| every other endpoint | — | unchanged; the change is additive |

The new path sits under `/api`, so the existing rate-limit classification charges it to the create
budget (SPEC rule 9). Nothing is reserved by the change: short codes are 8 characters and live at
`/{code}`, never under `/api`.

## Impacted schema and data

- **No schema change.** Paging is by the existing primary key, newest first. H2 walks the primary
  key backwards ("index sorted") and reads `limit + 1` rows for any page, the first or one a
  million rows deep (P5: `scanCount` 51 and 52 on 1 000 000 rows). The index
  `01-create-redirect`'s design expected is not needed, so no migration and no Flyway number.
  `02-click-retention` takes none either, so the next number stays free.
- **Rows.** Read only. The application still has exactly one statement that writes `audit_log`, an
  `INSERT`, in `AuditLog`. The new `SELECT` is the first read.
- **Rollback.** `git revert` of the merge commit. There is no schema or data to undo.

## Impacted data flows

| Flow | Change |
|---|---|
| Create, retire → audit `INSERT` in the same transaction | none |
| Redirect, statistics, click recording | none |
| **New:** Operator → `RequestIdFilter` → `RateLimitFilter` (create budget) → `AuditController`: loopback check → `AuditTrail` keyset `SELECT` → JSON page | design §4 |
| Startup | Tomcat no longer turns native forwarded-header handling on, even when Boot detects a cloud platform (`server.forward-headers-strategy=none`). In the shipped deployments (jar, compose) the strategy was already off, so nothing changes there (P4, default row) |

## Blast radius

| If this is wrong | Worst case | Detection |
|---|---|---|
| The loopback rule admits a remote client | link targets and request ids exposed to the network | AC-11 to AC-14; the security review; P4b, which shows the platform-default hole this design closes |
| A future deployment re-enables forwarded headers (`SERVER_FORWARDHEADERSSTRATEGY=native`, or removes the pin) | after design review DR-01: the audit read **closes**, with every request `403`, because the controller admits only under an effective `NONE` strategy (P6). Before that fix, the hole of P4b returned | functional tests for both overrides and the shipped pin, and a real-Tomcat test with `spring.main.cloud-platform=kubernetes` (design §7) |
| Paging repeats or skips committed rows | an Operator misses or double-counts a mutation | AC-6, AC-8, AC-20 (P3 by effect) |
| A read writes something | the trail grows on reads, or a row changes | AC-10; `AuditTrail` holds only a `SELECT` |
| A read leaks into logs | targets in the log stream | AC-15, AC-16; no new log event; the cursor and the content are never logged |
| The store fails | an empty page mistaken for an empty trail | AC-21: the inherited catch-all `500`, never a page |
| Rate-limit or proxy behaviour changes for other paths | other clients see a different `429` | unchanged in the shipped deployments (P4, default row); `RateLimitJourneyTest` and `TrustedProxyJourneyTest` run unchanged |

## Compatibility (FR-13)

- **Links, codes, redirects, statistics.** Untouched: no shared code path changes. The only shared
  configuration change, the forwarded-header strategy, keeps the shipped deployments' behaviour
  (P4, default row).
- **Stored audit rows.** Read as stored. `before` and `after` are parsed from the JSON text the
  service itself wrote, and nothing is masked or derived (SPEC rule 3; P2b shows a create row and
  a retire row).
- **Clients.** The change is additive: one new path. The API document gains one operation, and
  every existing operation is unchanged (AC-19).
- **An upgraded data directory.** No migration; the existing rows are read as they are (AC-18).

## Test impact

**Added.**
- Functional classes, on their own in-memory database so AC-1's empty trail is real: AC-1 to
  AC-16, AC-19 to AC-21, and AC-18's journey (design §7).
- One real-Tomcat class for the forwarded-header pin.
- Unit tests for the limit and cursor parsing and the loopback test.

**Changed.** None. `OpenApiDocumentTest` compares the committed document with the generated one.
The document is regenerated in this slice (territory), and the test itself is unchanged.

**Functional suite: unchanged (AC-17).**
- `AuditJourneyTest` (AC-22 to AC-25 of `01-create-redirect`) checks rows, rollbacks and
  append-only writes, and never enumerates endpoints.
- `LinkCreateJourneyTest`, `LinkReadRetireJourneyTest`, `IdempotencyJourneyTest`,
  `StatsJourneyTest` and `RateLimitJourneyTest` read `audit_log` directly and are untouched by a new
  read path.
- `TrustedProxyJourneyTest` runs on MockMvc, which never runs Tomcat's valve, so the pinned
  strategy cannot change it.

**Removed.** None.

## Observability impact

- No new log event. Each request on the new path writes the existing INFO `request completed`
  (status only, with `requestId`).
- A `400`, `403` or `405` writes nothing else.
- A `500` writes the existing ERROR `request failed` with class names and one code frame. It never
  carries the message, the SQL, the cursor or audit content (ADR-0002, ADR-0004).
- No metric beyond `http.server.requests` with the route template `/api/audit`.
- Operator documentation goes into `docs/DESIGN.md` §3 (mine):
  - the endpoint;
  - loopback only, with no setting to open it;
  - the trust boundary for a local relay (SPEC rule 2);
  - the pinned forwarded-header strategy.

  `README.md` lists the endpoints and is outside this slice's territory. Design §9 asks the lead
  for a one-line grant, as `02-click-retention` does for its setting.

## Risks and mitigations, ranked

| # | Risk | Mitigation | Owner step |
|---|---|---|---|
| 1 | The trail is reachable from beyond loopback (NFR-S6) | peer address and no forwarding header, checked in the controller; forwarded-header handling pinned off (P4b: without the pin a Kubernetes-detected platform admits a forged `X-Forwarded-For: 127.0.0.2`); no setting opens it | design → QA (AC-11 to AC-14, the real-Tomcat test) → security review |
| 2 | Paging misses or repeats rows | keyset on the primary key, read-committed, `limit + 1` fetch; P3 shows the held-write case | design → QA (AC-6, AC-8, AC-20) |
| 3 | Audit content in logs or error bodies | no new event; the `cursor` is parsed by hand, so no framework conversion message carries it; problem bodies have no `detail` | QA (AC-15, AC-16, AC-21) |
| 4 | A shipped behaviour changes | additive endpoint; the pin keeps the shipped deployments' behaviour | QA (AC-17, AC-18) |
| 5 | Ordered custody | this slice holds `application.properties` and `openapi.json` first; it takes no Flyway number | integrate |
